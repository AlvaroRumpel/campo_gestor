<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter client → PostgREST / RPC | Everything the client sends is attacker-controllable; the repository is a convenience layer, never a security boundary |
| Repository → widget layer | Values returned here are rendered directly; a wrong percentage is a silent correctness failure, not a crash |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-08 | Elevation of Privilege | `createAtf` sending a client-chosen `propertyId` | medium | mitigate | The direct insert is gated by the `veterinarian_can_insert_atf_batch` RLS policy (05-01), which re-checks `is_member_of` and `get_role` server side; the client value is a hint, never a grant |
| T-05-09 | Tampering | `saveDgRecords` sending a `result` outside the three allowed values | medium | mitigate | `dg_records_result_check` (05-01) plus the RPC's own per-record validation (05-03); the Dart side only ever emits `DgResult.dbValue` |
| T-05-10 | Information Disclosure | `fetchEligibleAnimalsForAtf` leaking an ATF name from another property in the `blockedByAtfName` field | medium | mitigate | The query is scoped by `property_id` and the `members_can_read_atf_batches` SELECT policy applies to the embedded resource, so a non-member's ATF name is never returned |
| T-05-11 | Tampering | Percentage drift between AtfCard, AtfHeaderCard, and the progress bar showing different numbers for the same ATF | low | mitigate | `summarizeDg` is the single implementation; all three surfaces call it rather than recomputing |
| T-05-12 | Repudiation | A DG correction overwriting the earlier record, erasing the audit trail of what the vet originally palpated | high | mitigate | `saveDgRecords` only ever INSERTs; there is no update or delete method on `dg_records` in this repository, and 05-01 grants no UPDATE/DELETE policy |
</threat_model>
