<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local migration files → the live production-adjacent database | An applied migration is irreversible without a compensating migration |
| Access token / database password → shell environment | A credential supplied here has full schema authority on the project |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-54 | Tampering | Applying migrations out of order, so the RPC file references tables that do not yet exist | high | mitigate | The task applies `20260804` before `20260805` explicitly, and the filenames sort in that order for `supabase db push` |
| T-05-55 | Denial of Service | A failed partial apply leaving the schema half-migrated and the app broken | high | mitigate | Each migration file runs in a transaction; a failure rolls it back. The verification step queries for the objects rather than trusting the exit code |
| T-05-56 | Information Disclosure | A `SUPABASE_ACCESS_TOKEN` or database password leaking into a committed file or shell history | high | mitigate | The token is supplied as an environment variable only; no credential is written to any file in this plan, and `files_modified` is empty |
| T-05-57 | Tampering | Editing a migration to make a failing push succeed, silently weakening an invariant | high | mitigate | The task explicitly forbids working around a failure; the only sanctioned outcomes are a clean apply or a recorded blockage |
| T-05-58 | Repudiation | The phase reporting verified while the live schema is absent, because Flutter tests are green | high | mitigate | This plan is the phase's blocking gate: the checkpoint is `gate="blocking"` and `autonomous: false`, so the phase cannot auto-advance past it |
</threat_model>
