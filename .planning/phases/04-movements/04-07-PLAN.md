<objective>
Close the MOV-02 cross-property bypass on the `lots` table — the exact mirror of the animals fix delivered in gap cycle #2 (04-06). This bypass was previously DOCUMENTED-DEFERRED as an accepted MVP risk in 04-CONTEXT.md; per the user decision (2026-07-16) the scope is REVERSED and it is now being CLOSED (gap cycle #3, plan 04-07).

The RLS UPDATE policy `veterinarian_can_update_active_lot` (20260514_03_lots_animals.sql:40-50) WITH CHECK validates only `is_member_of(property_id)` + veterinarian role — it NEVER inspects `paddock_id`. The `move_lot_to_paddock` RPC (20260519_04_movements.sql) validates same-property, but it is a VOLUNTARY path: a veterinarian who is a member of two properties can bypass it entirely with a raw `PATCH /lots?id=eq.<id> {"paddock_id":"<paddock in a different property>"}` — WITH CHECK passes (property_id unchanged, vet is a member) and the lot is pointed at a foreign-property paddock. This is the identical bug class as CR-01/SC-4 (animals), on lots.

Fix: enforce the invariant "a non-null lots.paddock_id must belong to the lot's own property_id" with a `BEFORE INSERT OR UPDATE` trigger — mirroring `trg_animals_lot_same_property` (20260716_04_animal_lot_property_trigger.sql) exactly. The trigger fires on every write path (RPC, raw PATCH, any future caller); the RPC's own EXISTS check becomes defense-in-depth for a fast, clear error.

Purpose: close a confirmed multi-tenant isolation hole at the database trust boundary, access-path-independently, satisfying the MOV-02 atomic-move guarantee against tampering.
Output: one new trigger migration, lots assertions added to the existing pgTAP suite (authored for run-on-push), and the deferred-lots risk in CONTEXT.md updated to CLOSED.
</objective>
