Leituras:
- `Future<List<PropertyMember>> fetchMembers(String propertyId)` — `.rpc('list_property_members', params: {'p_property_id': propertyId})`, mapeando a `List` para `PropertyMember.fromJson`. Comentário registrando que isto **não** pode ser um `.from('property_members').select()`: a policy `members_read_own_memberships` só devolve as linhas do próprio usuário, e `auth.users.email` não é legível por `authenticated`.
- `Future<List<Invite>> fetchPropertyInvites(String propertyId)` — `.from('invites').select().eq('property_id', propertyId).eq('status', 'pending').order('created_at')`, autorizado pela policy `managers_can_read_property_invites`.
- `Future<List<MyInvite>> fetchMyInvites()` — `.rpc('list_my_invites')`. Comentário registrando que precisa ser RPC porque o convidado ainda não é membro e a RLS de `properties` esconderia o nome da fazenda.

Escritas (todas `Future<void>`, todas passando pelo `.rpc(...)`):
- `createInvite({required String propertyId, required String email, required String role})` → `create_invite` com `p_property_id`, `p_email`, `p_role`
- `revokeInvite(String inviteId)` → `revoke_invite` com `p_invite_id`
- `acceptInvite(String inviteId)` → `accept_invite` com `p_invite_id`
- `declineInvite(String inviteId)` → `decline_invite` com `p_invite_id`
- `removeMember({required String propertyId, required String userId})` → `remove_member` com `p_property_id`, `p_target_user_id`
- `updateMemberRole({required String propertyId, required String userId, required String newRole})` → `update_member_role` com `p_property_id`, `p_target_user_id`, `p_new_role`
- `leaveProperty(String propertyId)` → `leave_property` com `p_property_id`

`acceptInvite` e `declineInvite` recebem **apenas** o id do convite — nenhum parâmetro de e-mail. Comentário registrando que a identidade é derivada no servidor por `current_user_email()`.

Rodapé de providers:
