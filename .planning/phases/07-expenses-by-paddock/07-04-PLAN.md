<objective>
Build the data-access layer for gastos: an `ExpenseRepository` that mirrors `DoseRepository`'s
direct-table CRUD shape 1:1 (D-25), the providers the UI consumes, and the pure merge function
that folds the Phase 6 sanitary rows into one date-ordered list (D-29, D-30, D-32, D-33).

Purpose: this plan is where the phase's cross-module coupling actually lands. The merge is the
only place `sanitary_applications` and `expenses` meet, and doing it in Dart over two
already-scoped fetches keeps both tables independent while making the D-18 property — the total
is the sum of what is on screen — structurally true.

Output: one repository file with four providers and one pure merge function, plus a unit test
for the merge.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter client → PostgREST `/rest/v1/expenses` | Every repository call crosses into a surface where RLS is the only authorization; the client cannot be trusted to have filtered correctly |
| PostgREST 2xx response → "saved" in the UI | A 0-row UPDATE is answered 2xx; without `.single()` the client cannot distinguish a rejected write from a successful one |
| Phase 6 sanitary reads → Phase 7 totals | A wrong paddock attribution here silently produces a wrong financial figure with no error anywhere |
