## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user keystrokes → `numeric(14,2)` column | Free-text valor input crosses into a financial column; a mis-parse writes a wrong number with no error anywhere |
| user tap → irreversible-looking data loss | The delete affordance is one tap away on a phone held in a field |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-19 | Tampering (data integrity) | valor parsing | high | mitigate | `FilteringTextInputFormatter` restricts the character set, `_parseDouble` normalises the comma, the validator rejects empty/unparseable/zero/negative, and `CHECK (amount > 0)` from 07-01 is the server-side backstop. Task 3 asserts the `1240,50 → 1240.50` conversion and both rejections |

| T-07-21 | Elevation of Privilege | dialog reachable by a `reader` | high | mitigate | The dialog is only opened from controls that 07-06/07-07 render behind `canManageExpenses`; the actual enforcement is the `owner_vet_can_insert_expense` / `owner_vet_can_update_expense` RLS policies from 07-01, which reject a reader's write regardless of how the dialog was reached |
