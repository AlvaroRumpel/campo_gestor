Append three trigger functions and their triggers to the same migration file.

`enforce_atf_membership_valid()` — `RETURNS trigger LANGUAGE plpgsql SET search_path = public`.
Selects `category` and `property_id` from `animals` into local variables for `NEW.animal_id` where
`deleted_at IS NULL`. Raises with ERRCODE `23503` when the animal is not found or archived; raises
with ERRCODE `23503` when the animal's property differs from `NEW.property_id`; raises with ERRCODE
`23514` when the category is not in the two-value set (`vaca`, `novilha`) — the eligible categories
per REPR-02's business rule, out of the seven in `lib/features/animais/data/animal_constants.dart`.
Also select `property_id` from `atf_batches` for `NEW.atf_batch_id` and raise with ERRCODE `23503`
when it differs from `NEW.property_id`, so the membership cannot straddle two properties from either
side. Returns NEW. Wire it as `trg_atf_membership_valid BEFORE INSERT OR UPDATE ON
animal_atf_memberships FOR EACH ROW`. Do NOT add `pg_advisory_xact_lock` — nothing here generates a
sequence, and the partial unique index already handles the one real concurrency hazard
(RESEARCH Pitfall 3).

`enforce_dg_record_same_property()` — same shape. Verifies that the `property_id` of the referenced
`atf_batches` row and of the referenced `animals` row both equal `NEW.property_id`, raising with
ERRCODE `23503` on any mismatch. Wire it as `trg_dg_records_same_property BEFORE INSERT OR UPDATE ON
dg_records FOR EACH ROW`.

`deactivate_atf_membership_on_baixa()` — `RETURNS trigger LANGUAGE plpgsql SET search_path = public`.
Sets `active = false` on every `animal_atf_memberships` row for `NEW.id` that is currently active,
then returns NEW. Wire it as `trg_animals_baixa_deactivates_atf AFTER UPDATE OF deleted_at ON animals
FOR EACH ROW WHEN (OLD.deleted_at IS NULL AND NEW.deleted_at IS NOT NULL)`. This implements D-19's
"na mesma transação" requirement at the table boundary rather than inside the `register_baixa` RPC —
a deliberate divergence from 05-RESEARCH.md's code sample, chosen because the trigger holds on any
write path (including a raw PostgREST PATCH of `animals.deleted_at`), which the RPC-only version does
not, and because it removes the second UPDATE statement from the RPC. Record that rationale in a
comment above the trigger. Per D-16 the membership row is soft-deactivated, never deleted, so the
animal's DG history in that ATF stays queryable and correctable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter client → PostgREST | An authenticated veterinarian's JWT is valid for every property they are a member of; any table-level grant is reachable by a hand-crafted request, not only by this app's UI |
| PostgREST → Postgres tables | RLS `WITH CHECK` evaluates only the row being written; it never inspects a referenced row's `property_id` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Tampering | `animal_atf_memberships` raw POST/PATCH | high | mitigate | No INSERT/UPDATE/DELETE policy exists on the table; the only write path is the SECURITY DEFINER RPC set added in 05-03 (Task 1) |
| T-05-02 | Tampering | `animal_atf_memberships.animal_id` pointing at another property's animal | high | mitigate | `trg_atf_membership_valid` compares `animals.property_id` and `atf_batches.property_id` against `NEW.property_id` on every INSERT and UPDATE (Task 2) |
| T-05-03 | Tampering | Adding a `touro`/`terneiro` to an ATF, bypassing the UI category filter | medium | mitigate | `trg_atf_membership_valid` raises ERRCODE 23514 for any category outside {vaca, novilha} (Task 2) |
| T-05-04 | Tampering | `dg_records` raw POST with a forged `property_id` or a cross-property `animal_id` | high | mitigate | SELECT-only RLS on `dg_records` plus `trg_dg_records_same_property` (Tasks 1 and 2) |
| T-05-05 | Information Disclosure | Reading another property's ATF roster or DG history | high | mitigate | `is_member_of(property_id)` SELECT policies on all three tables, with `FORCE ROW LEVEL SECURITY` so even a table owner is subject to them (Task 1) |
| T-05-06 | Repudiation | Membership silently vanishing after an animal baixa, losing the record that the animal participated | medium | mitigate | D-16/D-19: the membership row is soft-deactivated (`active = false`), never deleted, by `trg_animals_baixa_deactivates_atf` (Task 2) |
| T-05-07 | Denial of Service | Unbounded `dg_records` growth from repeated re-saves | low | accept | D-12 makes multiple DG rows per animal intentional; the client only submits changed rows (05-UI-SPEC `## Interaction Contracts`), and farm-scale volumes make this a non-issue |
</threat_model>

  and 05-UI-SPEC.md E3.
- **A-EDGE-REPR-03** — Same classification miss for REPR-03. Edge behaviors derived by hand from
  ROADMAP SC-3 and 05-UI-SPEC.md E6.
- **A-SCHEMA-01** — `animal_atf_memberships` is assumed to be empty in every environment, so
  `ADD COLUMN property_id uuid NOT NULL` needs no backfill. It was created as a Phase 2 skeleton with
  no policies (reads and writes blocked), so no row can have been inserted through the app. If the
  `supabase db push` in 05-10 fails on a NOT NULL violation, this assumption is wrong and the column
  must be added nullable, backfilled, then set NOT NULL.
- **A-BAIXA-01** — D-19's membership deactivation is implemented as an `AFTER UPDATE OF deleted_at`
  trigger rather than inside the `register_baixa` RPC as 05-RESEARCH.md sketched. This is stronger
  (path-independent) and smaller, but it means any future non-baixa soft-delete of an animal would
  also drop its ATF membership. Today baixa is the only path that sets `animals.deleted_at`.
