<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → Postgres RPC | Every sanitary write crosses here; the client controls the animal id list, dose id, lot id and date |
| authenticated client → PostgREST table endpoints | Direct table reads/writes on `doses` and `sanitary_applications` bypass the RPCs entirely |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Tampering | `sanitary_applications` frozen row | high | mitigate | pgTAP asserts UPDATE and DELETE both raise via `trg_snapshot_immutable`, and that the table carries exactly one policy whose command is SELECT |
| T-06-02 | Tampering | client-submitted totals | high | mitigate | pgTAP asserts stored `total_ua`/`total_volume`/`total_cost`/`animal_count` equal fixture-derived values, so a client-supplied total could never have been persisted |
| T-06-04 | Elevation of Privilege | `register_sanitary_application` | high | mitigate | pgTAP asserts SQLSTATE 42501 for a reader member and for a veterinarian of a different property |
| T-06-05 | Tampering | double reversal | medium | mitigate | pgTAP asserts P0003 from the RPC pre-check and 23505 from the unique index on a direct insert |
| T-06-08 | Repudiation | unattributable application | medium | mitigate | pgTAP asserts `applied_by` equals the calling user id, proving it is server-derived |

No package-manager installs occur in this phase (zero new pub.dev dependencies per 06-UI-SPEC.md
Registry Safety), so no supply-chain threat row or legitimacy checkpoint applies.
