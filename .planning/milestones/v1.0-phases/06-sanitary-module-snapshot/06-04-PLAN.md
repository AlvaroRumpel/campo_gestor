  <action>
    Create `lib/features/sanitario/data/sanitary_application_exception.dart`.

    Define an enum with exactly four values: a forbidden-role case, a composition-changed case, an
    already-reversed case, and a catch-all invalid-state case. Four reasons is the whole vocabulary
    the three write surfaces branch on; do not add a fifth.

    Define `SanitaryApplicationException implements Exception` with final reason and final message
    fields, a const constructor, and a `toString` returning the message.

    Define a factory taking the driver's `PostgrestException` plus a required named
    `fallbackMessage`. The fallback is required because the UI-SPEC gives three different
    generic-failure strings — one for registration, one for estorno, one for dose save — and
    hard-coding any single one here would put the wrong sentence on two of the three screens.

    Mapping by SQLSTATE: 42501 becomes the forbidden reason carrying the locked role-refusal string;
    P0002 becomes the composition-changed reason carrying the server's own message verbatim, because
    the raised text already is the exact pt-BR concurrency template with the count substituted;
    P0003 and 23505 both become the already-reversed reason carrying the locked already-estornada
    string; every other code becomes the invalid-state reason carrying the supplied fallback.

    Add a top-level helper that takes an arbitrary caught `Object` plus the same required fallback,
    returns the exception unchanged when it already is one, routes a `PostgrestException` through the
    factory, and otherwise returns an invalid-state exception with the fallback — so every catch
    block in the widgets is one line and no raw database text can reach a screen.

    This file may import the Supabase package for the `PostgrestException` type: it is a data-layer
    error-mapping utility, not a widget or a repository, and mapping the driver's exception type is
    precisely its job.
  </action>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-02 | Tampering | client-submitted totals | high | mitigate | The repository's write methods accept no total, UA, volume or cost parameter at all — the RPC signature has no such parameter to pass one to |
| T-06-04 | Elevation of Privilege | write attempted by a non-veterinarian | high | mitigate | Repository does not gate; the RPC raises 42501 and the exception class maps it to the locked pt-BR refusal, so a bypassed UI gate still fails safely and legibly |
| T-06-06 | Information Disclosure | cross-property application reads | high | mitigate | Every read goes through the SELECT policy; the property-scoped list additionally filters by the id resolved from `currentPropertyProvider` |
| T-06-10 | Information Disclosure | raw Postgres error text surfaced to the user | medium | mitigate | `asSanitaryException` funnels every caught object into one of four reasons with an authored pt-BR sentence; only the P0002 branch passes server text through, and that text is itself an authored template |

ASVS level 1; blocking severity is high. No new packages, so no supply-chain row.
