<objective>
Close ROADMAP Phase 4 Success Criterion 4 ("Tentativa de mover animal para lote de propriedade diferente é rejeitada pelo RLS/RPC com erro claro") at the database, access-path-independently.

The first gap cycle (04-04/04-05) added the `move_animal_to_lot` RPC and rewired `AnimalRepository.moveAnimal` to call it — but a DEEP code review (04-REVIEW.md, CR-01 reopened) proved the RPC is a VOLUNTARY path. The RLS UPDATE policy `veterinarian_can_update_active_animal` (20260514_03_lots_animals.sql:79-89) WITH CHECK validates only `is_member_of(property_id)` + veterinarian role — it never inspects `lot_id`. A veterinarian who is a member of BOTH properties (the app's core multi-property-vet case) bypasses the RPC entirely with a raw `PATCH /animals?id=eq.X {"lot_id":"<lot in a different property>"}` — WITH CHECK passes (property_id unchanged) and the cross-property assignment succeeds. SC-4 is NOT met.

Fix: enforce the invariant "a non-null animals.lot_id must belong to the animal's own property" with a `BEFORE INSERT OR UPDATE` trigger — the project's native idiom (snapshot immutability already uses a BEFORE trigger, 20260508_02:198-210). The trigger guards the RPC, raw PATCH, and any future write path. This supersedes D-04's RLS-only approach; the RPC's own EXISTS check (from 04-04) becomes defense-in-depth for a fast, clear error message. Also fix WR-01 (TOCTOU: the RPC's final UPDATE never re-checks `deleted_at`).

SCOPE (LOCKED): animals only. The IDENTICAL raw-write bypass for MOV-02 (`veterinarian_can_update_active_lot` never inspects `paddock_id`; `move_lot_to_paddock` bypassable via raw `PATCH /lots {paddock_id:...}`) is DOCUMENTED-DEFERRED as an accepted MVP risk this cycle — NOT fixed.

Purpose: satisfy an explicit, numbered roadmap success criterion that is currently unmet at the trust boundary.
Output: one new trigger migration, a WR-01 amendment to the move_animal_to_lot migration, a pgTAP test authored for run-on-push, and the deferred-lots risk recorded in CONTEXT.md.
